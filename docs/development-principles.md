# 开发原则

> 本文档是写代码、做评审、交付现场时的**底线**。违反原则的代码不应合并，不应交付。

---

## 核心信条

### 1. 不敷衍自己，不敷衍用户

- 每一行代码都要能向自己解释清楚**为什么这样写**。
- 用户在现场用的是**工控环境**，一次糊弄可能导致远程产线停摆。
- 文档、注释、日志信息要对**接手的人**友好，不写只有自己看得懂的缩写和魔法数。

### 2. 认真完成，不留坑

- **禁止**「先凑合能跑，以后再改」式提交；v1.0 规划里的底座能力**不得后置**。
- 临时方案如果不可避免，必须在 `docs/dev-log.md` 记录：原因、风险、偿还计划。
- 公开 API、配置项、数据库字段一旦定下，变更要有迁移或兼容说明。
- 发现问题**当场修**；能一并修复的关联问题不要拆成「下次再说」。

### 3. 实事求是

- 不知道就是不知道：去**读代码、写测试、加日志**验证，不要凭感觉改。
- 性能、安全、兼容性 claims 要有**依据**（测试数据、日志、文档引用）。
- 文档与代码**不一致时，以代码为准并立即改文档**。

### 4. 验证手段（杜绝糊弄、猜测、将就）

| 情况 | 正确做法 | 禁止 |
|------|----------|------|
| 逻辑不确定 | 写**单元测试**覆盖正常/边界/失败路径 | 手动点一下就当完成 |
| 并发/网络问题 | 测试 + **结构化日志**埋点，复现后再改 | 加 `sleep` 碰运气 |
| 配置行为 | 用默认配置和非法配置各跑一遍 | 「应该可以吧」 |
| 安全相关 | 对照 `docs/meta-plan.md` 安全测试清单逐项过 | 跳过「反正内网」 |
| 跨平台 | 至少在目标平台或 CI 交叉编译通过 | 只在自己电脑上验 |

**原则**：可以用测试用例验证，可以用日志埋点验证，但**绝不允许**糊弄、猜测、将就。

## 工程优先级（与产品原则一致）

```
安全  >  简单  >  快
```

- 不为「快」删掉鉴权、审计、输入校验。
- 不为「简单」把管理口默认暴露公网（`allow_public_bind` 默认 `false`）。
- 性能优化在**正确性证明之后**再做。

## 代码与模块规范

### 目录与依赖

- 严格按 [meta-plan.md](meta-plan.md) 的 `internal/` 分层；**底座先写，上层后组装**。
- 底座模块（logger、safeutil、transport）**不得**依赖 api/web/sessionmgr。
- 所有长期 goroutine 必须经 `safeutil.GoSafe` 包装。

### 错误处理

- 错误**向上返回**或记录后做明确降级；禁止无声 `_ = err`。
- 用户可见错误信息要**指明字段/步骤**；内部错误打堆栈日志。
- 敏感信息（密码、私钥、token）**禁止**出现在日志和 API 响应（用 `redact`）。

### 配置

- 首次启动生成的 YAML 必须带**完整中文注释**。
- 新增配置项：更新 `defaults.go` 模板 + `docs/deploy.md` 说明 + 必要时 `dev-log`。

### 测试

- 底座与协议层（frame、crypto、bindcheck）**必须有单元测试**。
- 修 bug 时**先写失败测试**再修（能写的情况下）。
- `go test ./...` 应在 CI / 提交前通过。

### 注释

- **语言**：中文。
- **要求**：读注释就能知道这段代码做什么、在什么场景下被调用；导出符号、SQL 表/字段、复杂分支必须注释。
- 使用统一 `internal/logger`；分级：TRACE/DEBUG/INFO/WARN/ERROR/FATAL。
- 连接建立/断开、鉴权失败、配置加载、NAT 操作等**关键路径**必须有 INFO 及以上日志。
- DEBUG/TRACE 用于开发验证，生产默认 info。

## 增量开发：做一步测一步（避免返工）

> **不要等全部写完再测。** 每完成一个 step（或 step 内的子模块），立刻验证，通过后再进入下一步。

| 时机 | 必做动作 |
|------|----------|
| 开始新 step / 新增第三方依赖 | `go mod tidy`，确认 `go.sum` 与 import 一致 |
| 完成一个模块 | `go test ./internal/<pkg>/...` 通过，或本地跑通并检查日志埋点 |
| 完成一个 step | `go test ./...`（至少覆盖本 step 包）+ 更新 dev-log / 记忆.md |
| 修 bug | 能写则先写失败测试，再修代码 |

**验收底线**：未跑测试、未看日志、未 `go build` 通过的代码，不得标记 step 完成。

## 开发阶段执行要求

开发顺序见 [meta-plan.md](meta-plan.md) **「开发执行顺序」**，**禁止跳步**。

| 阶段 | 名称 | 完成标准 |
|:----:|------|----------|
| step1 | 底座工具包 | logger + safeutil 可用，有测试 |
| step2 | transport | 粘包测试、TLS 连接、重连逻辑可演示 |
| step3 | tun | Linux/Win/macOS 至少一端读写 IP 包成功 |
| step4 | crypto | 加解密单元测试通过 |
| step5 | 网络业务 | IP 池、SQLite、session、NAT 联调 |
| step6 | config | 首次生成 YAML 注释完整 |
| step7 | API + WebUI | 登录、用户、peer、监控页面可用 |
| step8 | security 等 | bindcheck、审计、自签证书 |
| step9 | 主程序组装 | server/client 端到端跑通 |
| step10 | 文档与打包 | release 脚本产出、deploy 文档可照着做 |
| step11 | 全场景测试 | meta-plan 测试清单全部勾选 |

**每完成一个 step**：

1. 在 [dev-log.md](dev-log.md) 追加一条记录（日期、做了什么、踩坑、待办）。
2. 更新 [记忆.md](../记忆.md) 里的「当前阶段」表格。
3. 若行为影响部署，更新 [deploy.md](deploy.md)。

## Code Review 自检清单（提交前过一遍）

- [ ] 是否遵守安全默认（管理口、分流、鉴权）？
- [ ] 是否有测试或日志证明改动正确？
- [ ] 是否引入未文档化的配置项？
- [ ] goroutine 是否 GoSafe？关闭路径是否优雅？
- [ ] 是否留下 TODO/FIXME 且无 dev-log 记录？
- [ ] 文档是否需要同步更新？

## 与 AI 协作时的要求

接手请先读 [记忆.md](../记忆.md) 中的阅读顺序。

对 AI 的要求同样适用本原则：

- 不要生成「占位实现」冒充完成。
- 不要猜测 API 行为，要读现有代码或写测试验证。
- 发现规划与实现矛盾时，**先记录 dev-log，再修文档或代码**，不要默默偏离。

### AI 禁止事项（硬性）

| 事项 | 规则 |
|------|------|
| **`VERSION` 文件** | **禁止** AI 修改、删除或提交；版本号**仅开发者**决定 |
| **`git commit` / `git push`** | **禁止** AI 擅自执行；仅当用户**当次明确指令**才可协助起草，且**不代为 commit** |
| **Commit 作者** | 提交者**只能是开发者本人**；禁止 `Co-authored-by`、AI 署名、任何协助者行 |
| **版本号写死** | 禁止在源码中硬编码版本；通过 `VERSION` + 构建 `-ldflags` 注入 |

## 开发环境

| 项目 | 要求 |
|------|------|
| 操作系统 | **Windows**（主开发环境） |
| Shell | **PowerShell 7**（`pwsh`） |
| Go | **1.26** |
| Windows 提权 | 本机有 `sudo`；TUN/路由/服务安装等用 `sudo` 执行构建产物或测试 |
| Git | 仅开发者提交；见上表 Git 规则 |

日常构建：

```powershell
.\scripts\build-local.ps1      # 本机快速 → bin/
.\scripts\build-release.ps1    # 全平台发版 → dist/
```

版本与发版流程见 [versioning.md](versioning.md)。
